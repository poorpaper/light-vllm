普通解码与投机解码，如何共用同一条执行路径

Scheduler 不给请求贴 prefill/decode 模式标签，只报告本轮已知输入、投机预留和最大输出数。同一个 LocalModelWorker 注入不同 DecodeHandler；Engine 最终只接收“算完多少输入、确认哪些 token、其中多少已经写入 KV cache”。

为什么 RequestOutput 需要两个计数维度

output_token_ids 表示已经确认、可以对用户可见的 token；num_cached_output_tokens 表示其中有多少已经随 target verify 写入 KV cache。前者决定事件流，后者决定本轮能提交多少 KV。

尚未写入缓存的确认 token 去哪里

Engine 仍把它追加到请求 token 列表，但 Scheduler 不把它计为 computed。下一轮它自然成为普通输入再计算一次。投机解码常见的 bonus 或 replacement token 可以使用这条路径，不需要新增专用 Engine。
